The Change Request Is the Product

John Terrill · LinkedIn · /writing/the-change-request-is-the-product

When people ask what Nexplane is, the shortest answer I can give them is this: we built a platform where the Change Request is the primary object in the system. Not a ticket. Not a log entry. Not a form. The CR is a structured, typed, executable object that carries the full lifecycle of a change — from the first statement of intent through to the verified outcome and whatever lessons came after. Everything else in the platform exists to make that object as good as it can be.

Most infrastructure tools treat the change request as a side artifact. You use a tool to do a thing, and separately you file a ticket saying you did the thing. The tool does not know about the ticket. The ticket does not know what the tool actually did. The compliance team reads the ticket. The engineering team reads the tool logs. Neither reads the same story. That disconnect is expensive and it compounds over time — every change that runs outside a coherent record is organizational memory that was never written down.

The CR should contain enough to reconstruct not just what happened, but why. Intent, scope, dependencies, risk assessment, blast radius, approvals, execution plan, verification criteria, rollback procedure, actual outcome. That is not a long list when you build a system around it. It becomes the natural shape of infrastructure work when the tooling supports it. When the CR is the primary object, engineers stop thinking of documentation as a tax. It becomes part of the workflow because the workflow runs through it.

The more interesting property is that this object should become smarter over time. A CR for rotating a set of credentials in 2026 should inform the risk model for rotating a different set of credentials in 2027. A failed rollback in one environment should surface as a warning the next time a similar change runs somewhere else. The change history is not an archive. It is training data for better decisions. That feedback loop is what separates a control plane from a change log.

This is why the Change Request is not a feature of Nexplane. It is the product. Everything we build is in service of making that object richer, more executable, more connected to the systems it touches, and more useful the second time than the first. If the CR is right, the audit trail is right, the rollback is right, and the organizational learning is right. If the CR is just paperwork, none of that follows.
